# 交通与住宿中心设计

日期：2026-09-19  
状态：待产品确认

## 1. 背景与目标

当前产品已能创建多日行程、编辑每天的活动、保存多份行程，并为地图与路线服务预留接口。下一步不是继续增加景点卡片，而是补齐“已经订了什么、什么时候出发、晚上住哪里”这一层，让一份计划能在出发前和旅行途中使用。

成熟产品通常把日程、交通、住宿和预订摘要放在一个行程中。Wanderlog 强调行程、地图、航班和酒店预订集中管理；TripIt 强调把各种渠道的预订整理成统一时间表；Polarsteps 也把路线、住宿、活动和预订放进同一计划。本阶段吸收这种信息结构，但不复制其视觉或商业功能。

本阶段目标：用户可以在一份行程中手动录入、修改和删除交通与住宿安排，查看准备度与明确的缺失提示，并与现有保存、撤销和未保存保护形成同一套闭环。

## 2. 范围

### 本阶段包含

- 交通安排：飞机、高铁/火车、长途汽车、轮船、自驾和其他。
- 住宿安排：酒店、民宿、青旅、亲友家和其他。
- 状态：计划中、已确认、已取消。
- 交通字段：出发/到达日期时间、地点、承运方、班次、预订编号、费用和备注。
- 住宿字段：名称、类型、入住/退房日期、地址、联系电话、预订编号、费用和备注。
- 行程详情中的“日程 / 交通住宿”切换。
- 准备度摘要：已确认数量、待确认数量、尚未覆盖的住宿夜晚。
- 明确的检查提示：时间倒置、交通与活动时间冲突、住宿夜晚缺口、日期超出行程范围。
- 交通和住宿按时间排序展示；取消的记录保留但不参与准备度与冲突计算。
- 复用现有撤销、未保存提示、保存失败保护和浏览器本地存储。

### 本阶段不包含

- 机票、车票或酒店搜索、比价、下单和支付。
- 航班动态、延误、登机口和价格实时更新。
- 邮箱自动导入、图片/PDF/二维码附件识别。
- 身份证、护照、完整乘客姓名等敏感证件信息。
- 账号、云同步、多人协作和跨设备同步。
- 费用分摊、完整预算流水和报销。
- 地图 API 实网联调。

这些能力分别进入后续 API、账户协作和预算子项目，避免本阶段同时引入外部服务与复杂权限。

## 3. 核心体验

### 3.1 页面入口

行程详情标题区下新增二级切换：

- `日程`：保留现有按天时间轴、地点编辑和地图双栏。
- `交通住宿`：显示准备度、检查提示、交通列表和住宿列表。

切换不会改变当前日期，也不会自动保存。用户在两个视图中的修改共用同一个“未保存”状态和“保存行程”按钮。

“我的行程”卡片增加简短准备状态，例如“2 项待确认”或“交通住宿已确认”，但不塞入完整详情。

### 3.2 交通住宿首页

顶部显示三个可快速理解的指标：

- 已确认：状态为“已确认”的有效记录数。
- 待确认：状态为“计划中”的有效记录数。
- 住宿覆盖：固定日期行程中已覆盖夜晚数 / 应覆盖夜晚数。

指标下方仅在需要时显示检查提示。提示是辅助信息，不阻止保存；字段本身不合法时才阻止提交。

页面主体分为“交通”和“住宿”两组。每条卡片显示用户执行旅行所需的摘要，详情可展开编辑。空状态提供单一明确入口：“添加交通”或“添加住宿”。桌面端表单为页面内双列表单，移动端改为单列，不使用难以正确管理焦点的自制弹窗。

### 3.3 新增与编辑

新增时先选择交通或住宿，再显示对应字段。编辑沿用同一表单。

必填规则：

- 交通：类型、出发地点、到达地点、出发日期时间、到达日期时间。
- 住宿：住宿类型、名称、入住日期、退房日期。
- 费用留空表示“未填写”，用户明确输入 0 表示“无需费用”；两者不会混为一谈，也不冒充实时价格。
- 日期时间必须有效，到达必须晚于出发，退房必须晚于入住。
- 名称、地点和备注设置合理长度上限，防止异常大数据占满浏览器存储。

预订编号、联系电话和备注为可选。界面提示这些数据只保存在当前浏览器，不建议填写证件号码或支付信息。

### 3.4 状态与删除

- “计划中”表示尚未预订或仍需核对。
- “已确认”表示用户自行确认过，不代表平台已向供应商验证。
- “已取消”保留记录，方便用户理解变更历史，但不计入准备度、住宿覆盖和冲突。
- 删除是本次未保存编辑的一部分，可通过现有“一步撤销”恢复；保存后不进入行程库回收站。删除前使用页面内二次确认，避免误触。

## 4. 数据设计

在 `Itinerary` 上增加可选字段，确保旧数据无需一次性重写：

```ts
type BookingStatus = "planned" | "confirmed" | "cancelled";

type TransportReservation = {
  id: string;
  kind: "transport";
  mode: "flight" | "train" | "coach" | "ferry" | "drive" | "other";
  status: BookingStatus;
  title: string;
  departure_at: string;
  arrival_at: string;
  departure_place: string;
  arrival_place: string;
  provider?: string;
  service_number?: string;
  confirmation_code?: string;
  cost?: number;
  notes?: string;
};

type StayReservation = {
  id: string;
  kind: "stay";
  stay_type: "hotel" | "homestay" | "hostel" | "friends" | "other";
  status: BookingStatus;
  title: string;
  check_in_date: string;
  check_out_date: string;
  address?: string;
  contact?: string;
  confirmation_code?: string;
  cost?: number;
  notes?: string;
};

type TravelReservation = TransportReservation | StayReservation;
```

`Itinerary.reservations?: TravelReservation[]` 缺省为 `[]`。记录采用判别联合，交通表单不能产生住宿字段，反之亦然。

日期时间使用用户看到的当地时间字符串（`YYYY-MM-DDTHH:mm`），首版不做跨时区换算；界面标注“当地时间”。跨时区自动换算和供应商时区校验留给外部交通 API 阶段。

首版不把预订费用自动写回现有预算分类，避免重复计算生成方案中已有的交通和住宿估算。交通住宿页单独显示“已录入预订费用”，并注明预算整合将在预算子项目完成。

## 5. 派生规则

实现为独立纯函数，不把计算结果重复写入存储：

- `validateReservation`：校验单条记录与长度边界。
- `sortReservations`：交通按出发时间、住宿按入住日期稳定排序。
- `getTripReadiness`：计算确认数、待确认数和住宿覆盖夜晚。
- `findReservationIssues`：计算日期范围、时间冲突和住宿缺口。

固定日期行程的住宿覆盖规则：从第一天日期到最后一天日期之间，每一个过夜夜晚都应被至少一个未取消的住宿安排覆盖。住亲友家同样算覆盖。日期未定时不生成“缺少哪晚住宿”的结论，只提示“日期确定后可检查住宿覆盖”。

交通与活动冲突只比较有明确日期、且处在相同行程日的记录；仅报告真实的时间重叠，不猜测交通耗时。跨午夜交通允许存在，只要到达时间晚于出发时间。

日期范围检查允许“前一晚出发、首日到达”和“末日出发、次日到达”：只要交通时间段与整趟旅行时间范围有交集就视为相关；完全发生在旅行前或旅行后的记录才提示可能填错行程。住宿同理，只要入住区间与行程日期有交集即可。

## 6. 组件与数据流

- `ItineraryView` 继续持有整份可编辑行程，增加当前视图状态和未提交的预订表单草稿。
- `TravelLogistics` 接收 `itinerary`、受控表单草稿和 `onChange(nextItinerary)`，不直接访问 localStorage。
- `ReservationEditor` 只负责展示受控表单、校验和提交。
- `ReservationCard` 负责摘要、状态和编辑入口。
- `lib/itinerary-reservations.ts` 负责增删改、排序、校验和准备度计算。
- `travel-store.ts` 的规范化逻辑接受旧行程没有 `reservations` 的情况，并对存在的记录进行结构校验。

数据流为：表单提交 → 纯函数生成新的 `Itinerary` → `ItineraryView.commit` → 标记未保存并支持一步撤销 → 用户点击保存 → 现有 `travel:library:v2` 原子写入。不会让子组件绕过当前保存保护。

## 7. 错误与恢复

- 表单字段错误显示在相关字段附近，焦点移到第一个错误字段。
- 存储写入失败沿用当前行为：保留页面修改，显示失败原因，可重试保存。
- 旧版行程缺少新字段时按空列表读取；结构损坏时沿用“保留原数据并重试”，不静默覆盖。
- 用户切换“日程 / 交通住宿”时，由 `ItineraryView` 保留未提交的编辑表单；切换行程或离开页面时沿用未保存提醒。
- 删除和取消是两个不同动作；取消不会造成信息丢失。

## 8. 测试与验收

### 自动化测试

- 旧行程迁移后仍能打开、编辑和保存。
- 交通和住宿的有效/无效日期边界。
- 跨午夜交通有效，倒序时间无效。
- 取消记录不进入准备度、住宿覆盖和冲突。
- 多段住宿正确覆盖夜晚，缺口只报告实际缺少日期。
- 交通与同日活动重叠时提示，不同日期不误报。
- 新增、编辑、取消、删除和一步撤销。
- 修改后显示未保存；保存失败不丢数据；重试后刷新恢复。
- 没有预订记录的空状态和旧行程兼容。

### 浏览器验收

- 桌面 1280×800：日程和交通住宿切换、双列表单、卡片布局。
- 手机 390×844：单列、44px 操作目标、无横向溢出。
- 完整路径：旧行程 → 添加交通 → 添加两晚住宿 → 查看准备度 → 制造并修正冲突 → 保存 → 刷新恢复。
- 错误路径：无效时间、存储失败、取消删除和未保存离开提醒。
- 无相关页面错误、框架错误覆盖层和控制台错误。

## 9. 完成标准

- 用户无需 API 即可完整记录一趟旅行的交通和住宿摘要。
- 页面能明确区分“计划中”“用户已确认”和“已取消”，不声称平台验证。
- 固定日期行程能指出真实的住宿覆盖缺口和明确时间冲突。
- 所有变更纳入现有保存、撤销和失败恢复机制。
- 旧数据可兼容，新数据损坏不会被示例数据覆盖。
- 首页、地图 API、账号、部署和完整预算系统保持不变。
