# 旅行预算中心设计规格

日期：2026-09-19  
状态：用户已确认  
范围：行程详情中的出发前预算计划，不包含实际消费记账

## 1. 背景

当前产品已经具备行程日程、交通住宿记录和本地行程库，但预算仍是生成阶段产生的一组静态汇总。用户无法调整各分类额度，也无法理解交通住宿预订费用和原估算之间的关系。

本功能在行程详情中新增“预算”工作区，让用户在出发前完成预算分配、查看计划支出来源，并识别未分配和超支风险。

## 2. 目标

- 默认以人均口径展示预算信息。
- 允许用户编辑交通、住宿、餐饮、门票、本地交通和其他六类预算额度。
- 分类额度合计可低于或高于总预算，但必须明确提示差额。
- 交通或住宿存在明确预订费用时，以预订费用替代对应分类的旧估算，避免重复计算。
- 支持“每人费用”和“整单费用”两种预订费用口径。
- 复用现有未保存、撤销、保存失败和离开提醒机制。
- 保持旧行程和当前 `travel:library:v2` 数据兼容。

## 3. 非目标

第一版不包含：

- 旅途中的实际消费流水；
- 多币种、汇率换算；
- AA 分账；
- 发票、报销管理；
- 实时价格、支付、订票；
- 账号、云同步或多人协作；
- 预算报表导出。

## 4. 信息架构

行程详情工作区调整为：

```text
日程 / 交通住宿 / 预算
```

“预算”页面包含四层信息。

### 4.1 顶部总览

展示：

- 每人总预算；
- 每人计划支出；
- 每人预计剩余或预计超支；
- 同行人数；
- 整团总预算与整团计划支出，作为辅助信息。

页面默认突出人均金额，整团金额使用次要层级，避免两种口径混淆。

### 4.2 分类预算

分类固定为：

1. 交通；
2. 住宿；
3. 餐饮；
4. 门票；
5. 本地交通；
6. 其他。

每个分类展示：

- 用户分配额度；
- 当前计划支出；
- 剩余额度或超支金额；
- 计划支出占分类额度的进度状态；
- 展开费用来源的入口。

编辑时金额按人均输入，保存到行程模型时换算为整团金额。

### 4.3 费用来源

费用来源解释当前计划支出的组成，例如：

- 南京到苏州车票：¥180/人；
- 平江路酒店：整单 ¥1,200，折合 ¥600/人；
- 门票：行程生成估算 ¥120/人；
- 餐饮：行程生成估算 ¥720/人。

费用来源只展示与预算相关的信息，不展示预订编号、联系电话、备注或其他敏感内容。
第一版只有交通住宿预订能够作为精确来源。现有景点条目费用与历史分类预算口径并不完全一致，因此餐饮、门票、本地交通和其他分类统一展示为“行程生成估算”，不得把活动条目伪装成可核对账单。

### 4.4 提醒区域

提醒包括：

- 分类额度合计低于总预算：“还有 ¥X/人尚未分配”；
- 分类额度合计高于总预算：“分类预算超出总预算 ¥X/人”；
- 分类计划支出超过额度：“{分类}预计超出 ¥X/人”；
- 部分交通或住宿没有明确费用：“当前金额可能不完整”；
- 交通住宿记录被取消后，预算统计已排除对应记录。

提醒不阻止用户保存。超额状态必须同时使用文字和视觉标记，不能只依赖颜色。

## 5. 数据模型

现有 `budget` 字段均按整团总额保存。继续保留该口径，避免破坏创建行程和旧版数据。

新增可选字段：

```ts
type BudgetCategory =
  | "transport"
  | "lodging"
  | "food"
  | "tickets"
  | "local_transport"
  | "other";

interface BudgetAllocations {
  transport: number;
  lodging: number;
  food: number;
  tickets: number;
  local_transport: number;
  other: number;
}

interface ItineraryBudget {
  // 现有字段保持不变
  total_available: number;
  estimated_total: number;
  remaining: number;
  transport: number;
  lodging: number;
  tickets: number;
  local_transport: number;
  food: number;
  other?: number;

  // 新增，可选以兼容旧数据
  allocations?: BudgetAllocations;
}
```

交通和住宿预订增加费用口径：

```ts
type CostScope = "per_person" | "total";

interface ReservationBase {
  // 现有字段保持不变
  cost?: number;
  cost_scope?: CostScope;
}
```

兼容默认值：

- 旧交通记录缺少 `cost_scope` 时按 `per_person` 处理；
- 旧住宿记录缺少 `cost_scope` 时按 `total` 处理；
- 旧行程缺少 `allocations` 时，以现有预算分类估算作为初始分类额度；
- 初始分类额度不强制补齐到总预算，差额显示为尚未分配。

## 6. 金额口径

底层统一使用整团金额计算和保存。

```ts
groupCost = cost_scope === "per_person"
  ? cost * travelers
  : cost;

perPersonCost = groupCost / max(travelers, 1);
```

规则：

- 金额允许为 `0`；
- `undefined` 表示未知，不得等同于 `0`；
- 金额必须为有限且不小于零的数字；
- 页面最多显示两位小数，整数不强制显示小数；
- 计算使用未格式化数值，显示阶段再格式化；
- 同行人数异常为零时使用 `1` 防止除零，但结构校验仍应拒绝非法行程数据。

## 7. 计划支出计算

### 7.1 交通与住宿

对未取消且填写了明确费用的记录进行整团换算。

- 存在至少一条有效交通预订费用时，交通计划支出使用所有有效交通预订费用合计，替代旧 `budget.transport`；
- 不存在有效交通预订费用时，继续使用 `budget.transport`；
- 存在至少一条有效住宿预订费用时，住宿计划支出使用所有有效住宿预订费用合计，替代旧 `budget.lodging`；
- 不存在有效住宿预订费用时，继续使用 `budget.lodging`；
- 已取消记录不参与；
- 没有费用的有效记录不参与合计，但触发“金额可能不完整”提示；
- 住宿未覆盖全部旅行夜晚时，继续显示现有住宿覆盖缺口，同时提示住宿金额可能不完整。

第一版采用分类级替代规则，不尝试把聚合旧估算拆分到具体车次或住宿晚数，以避免伪造精度。

### 7.2 其他分类

- 餐饮使用 `budget.food`；
- 门票使用 `budget.tickets`；
- 本地交通使用 `budget.local_transport`；
- 其他使用 `budget.other ?? 0`。

这些分类的来源统一标记为“行程生成估算”。现有 `ItineraryItem.cost` 继续服务于日程编辑和旧预算汇总，但第一版预算中心不使用它拆分分类来源，以免与历史聚合数据产生重复或不一致。

### 7.3 汇总

```ts
plannedTotal = transport
  + lodging
  + food
  + tickets
  + localTransport
  + other;

remaining = totalAvailable - plannedTotal;
allocationDifference = totalAvailable - sum(allocations);
```

预算中心使用派生值展示，不直接改写旧 `estimated_total` 和 `remaining`。只有现有日程编辑逻辑继续维护旧字段。这样可以保证旧页面行为稳定，同时让新预算中心使用更准确的预订替代规则。

## 8. 编辑、撤销与保存

- 分类额度编辑使用本地草稿；
- 用户确认额度后，通过 `ItineraryView` 现有 `commit()` 更新当前行程；
- 每次确认编辑形成一个可撤销步骤；
- 修改后显示“未保存”；
- 全局“保存行程”写入当前本地行程库；
- 保存失败时保留页面状态并允许重试；
- 页面内切换“日程 / 交通住宿 / 预算”不丢失未提交的预算编辑草稿；
- 存在未提交预算草稿时，全局保存提示先确认或取消编辑；
- 离开页面或刷新时复用现有未保存提醒。

## 9. 交通住宿表单变更

交通和住宿编辑表单在“费用”旁新增“费用口径”：

- 每人费用；
- 整单费用。

默认值：

- 新增交通默认“每人费用”；
- 新增住宿默认“整单费用”；
- 修改旧记录时使用第 5 节兼容默认值。

费用为空时仍可选择口径，但预算中心不把空值计入金额。

## 10. 存储兼容与损坏保护

- 不提升 `travel:library:v2` 键版本；
- 新字段保持可选；
- 读取旧数据时在内存中补出兼容默认值；
- 保存后写入完整新结构；
- `allocations` 必须包含六个非负有限数字；
- `cost_scope` 只能为 `per_person` 或 `total`；
- 存在非法新字段时，整份 v2 数据读取失败并保留原始内容；
- 不得过滤坏记录后静默覆盖。

## 11. 响应式与可访问性

桌面端：

- 顶部总览使用三到四列；
- 分类预算与费用来源可采用双栏；
- 保持当前薄荷色、细边框和低密度阴影。

手机端：

- 总览、分类和来源全部单列；
- 金额输入使用至少 44px 的触控高度；
- 不产生横向滚动；
- 展开分类后在当前分类下显示费用来源。

可访问性：

- 工作区使用 `tablist` / `tab`；
- 金额输入有明确标签、单位和错误关联；
- 超额同时显示文字和图标；
- 进度条提供可访问名称和数值；
- 错误提交后焦点移动到第一个无效字段；
- 键盘可以完成编辑、确认和取消。

## 12. 空状态与错误状态

- 无分类额度：从旧估算生成初始值；
- 总预算为零：仍允许编辑分类，但明确显示分类额度超出总预算；
- 无任何计划费用：显示“尚无可计算的计划费用”；
- 预订费用为空：显示“费用待补充”；
- 存储失败：显示错误并保留修改；
- 灵活日期：预算计算照常，住宿覆盖仍显示“日期确定后可检查”。

## 13. 测试与验收

### 13.1 纯计算测试

- 整单与每人费用换算；
- 交通住宿预订替代旧估算；
- 取消记录排除；
- 空值和零元区分；
- 分类未分配和超额；
- 分类计划支出超额；
- 单人和多人行程；
- 旧数据默认值。

### 13.2 存储测试

- 旧行程没有 `allocations`；
- 旧预订没有 `cost_scope`；
- 新结构保存并重开；
- 非法额度和非法费用口径不被静默覆盖；
- 存储写入失败不丢失当前修改。

### 13.3 组件与集成测试

- 编辑分类额度并确认；
- 未分配和超额提醒；
- 展开费用来源；
- 交通住宿费用口径切换；
- 工作区切换保留草稿；
- 撤销和保存闭环；
- 旧日程、地图、交通住宿与行程库回归。

### 13.4 真实浏览器验收

桌面视口 1280×800，手机视口 390×844：

1. 打开已保存的旧行程；
2. 进入预算页，确认人均和整团口径；
3. 调整分类额度并验证未分配或超额提醒；
4. 新增每人交通费用和整单住宿费用；
5. 确认预订金额替代旧估算；
6. 取消一条预订并确认统计更新；
7. 撤销、保存、刷新并确认数据恢复；
8. 检查无横向溢出、无相关控制台错误、无框架错误覆盖层。

## 14. 实施约束

- 不修改首页内容和首页交互；
- 不接入地图、酒店、航班或支付 API；
- 不部署 Netlify；
- 不引入新的主色、渐变或大型视觉资产；
- 不创建实际消费功能；
- 不把预订编号、联系电话或备注带入预算摘要。
