# 本地规划引擎 V2 设计规格

## 1. 背景与目标

当前创建行程页面可以记录出发地、目的地、日期、天数、人数、预算、节奏、兴趣与必去地点，但本地生成器主要复用固定苏杭模板。兴趣和必去地点没有完整参与编排，生成后也会立即保存，用户无法先检查结果。

本阶段在不接外部地图、AI、酒店或票务 API 的前提下，把创建链路升级为可解释、可预览、可保存的本地规划闭环：所有核心输入真实影响结果，系统只使用内置的已知地点和用户明确填写的地点，不编造未知城市的地址、坐标、营业时间或介绍。

成功标准：

- 用户填写的目的地、天数、日期、人数、预算、节奏、兴趣、必去地点和返程选择均反映在生成结果中；
- 生成结果先进入预览，明确确认后才保存到“我的行程”；
- 已知地点来自可审查的本地点位目录，未知地点保留为待定位的用户输入；
- 创建草稿和生成预览在刷新后可恢复；
- 保存失败不丢失预览，重复保存不产生重复行程；
- 现有行程详情、交通住宿、预算、撤销和行程库能力继续工作。

## 2. 范围

### 2.1 本阶段包含

- 本地地点目录与可解释的行程编排规则；
- 兴趣排序、节奏密度、必去地点锁定、多城市天数分配；
- 未收录城市和地点的待定位安排；
- 六类预算初始额度生成；
- 创建表单确认页、生成预览、返回修改、确认保存；
- 草稿与预览恢复、重复保存保护、存储失败保护；
- 桌面端和移动端创建、预览体验；
- 单元、组件、集成和真实浏览器验证。

### 2.2 明确不包含

- 地图地点搜索、路线计算或地址补全；
- AI 自动生成地点、游记或介绍；
- 实时天气、票价、营业时间、拥堵和供应商库存；
- 酒店、机票、火车票搜索、预订或支付；
- 账号、云同步、多人协作、分享链接和 PDF 导出；
- 首页改版和 Netlify 部署。

## 3. 核心产品原则

1. **真实优先。** 系统只展示内置目录中的事实字段或用户提供的文字。未知信息使用“待定位”“待确认”等明确状态。
2. **输入有结果。** 页面要求用户填写或选择的字段必须影响输出，不能只保存而不使用。
3. **先预览再保存。** 生成是可逆操作；只有“确认保存”才写入行程库。
4. **规则可解释。** 本地规划器输出稳定、可测试；相同输入产生相同日程内容，行程 ID 和生成时间除外。
5. **为 API 留边界。** 地点目录和规划器通过明确接口连接；以后可替换候选地点来源，不改创建页的业务流程。

## 4. 用户流程

### 4.1 填写

保留现有三步结构：

1. 基本信息：出发城市、目的城市、日期模式、出发日期、旅行天数、同行人数、是否返回出发地；
2. 旅行偏好：节奏、兴趣、每人预算、必去地点；
3. 生成前确认：完整展示规范化后的输入，不再称为“演示方案”。

目的城市和必去地点继续支持使用顿号或中英文逗号分隔。解析时去除首尾空白、忽略空项，并按首次出现去重。城市和地点名称保留用户输入的大小写与中文形式。

### 4.2 生成预览

用户点击“生成行程预览”后：

- 本地规划器生成一份尚未写入行程库的 `Itinerary`；
- 创建页切换到预览视图，不跳转到详情页；
- 预览展示路线、日期、人数、人均预算、每天城市与安排、必去/待定位标记、六类预算摘要；
- 用户可以选择“返回修改”或“确认保存行程”；
- 返回修改保留全部输入，并清除旧预览。再次生成以最新输入为准。

预览不是独立行程详情编辑器。本阶段不在预览中编辑单个地点、交通住宿或分类预算；保存后进入现有行程详情完成这些操作。

### 4.3 确认保存

- 点击“确认保存行程”时才调用现有行程库保存能力；
- 保存成功后清除创建草稿和预览缓存，选中该行程并进入现有详情页；
- 保存按钮在保存期间禁用，阻止重复提交；
- 同一个预览使用稳定的预览 ID，重复调用保存时由行程库按 ID 更新同一记录，不创建副本；
- 保存失败时停留在预览，显示可操作错误，保留所有内容并允许重试。

## 5. 本地点位目录

新增独立模块维护规划候选地点。每个地点至少包含：

```ts
type LocalPlace = {
  id: string;
  city: string;
  name: string;
  category: string;
  interests: string[];
  suggestedDurationMinutes: number;
  estimatedCostPerPerson: number;
  description: string;
  coordinate?: [number, number];
  verifiedHours: false;
};
```

首版目录仅整理当前项目已经使用的苏州、杭州地点，不为其他城市新增未经验证的景点。目录里的坐标只能沿用项目现有明确数据；营业时间统一不声称已验证。

地点目录提供按城市查询接口，不直接负责排序、天数分配或生成 `Itinerary`。

## 6. 编排规则

### 6.1 输入规范化

规划器接收完整 `TripDraft`。调用前统一：

- 目的地和必去地点去空、去重；
- 固定日期必须是有效的 `YYYY-MM-DD`；
- 天数限制 1–30，人数组限制 1–20；
- 每人预算必须为有限且不小于零的数字；
- 至少一个目的城市；
- 兴趣按界面选中顺序去重。

无效输入不进入规划器，由创建页展示具体字段错误。

### 6.2 城市天数分配

- 当旅行天数不少于目的城市数量时，每个城市至少分配一天，其余天数按目的地顺序轮转分配；
- 当旅行天数少于目的城市数量时，只能为前 `days` 个目的城市生成日程，预览明确提示其余城市未排入，并建议增加天数；
- 一天只归属一个城市，不伪造跨城半日路线；
- 路线仍记录全部用户目的地，便于用户发现未排入城市；
- 固定日期按日递增；日期未定时每天日期为 `null`。

### 6.3 必去地点

- 必去地点按用户输入顺序优先分配，且生成的安排 `locked: true`；
- 当名称命中当前城市的本地点位目录时，使用目录中的类别、时长、费用、描述和可用坐标；
- 当名称未命中目录时，创建用户地点安排：类别为“用户必去 · 待定位”，费用为 0，`verified_hours: false`，按现有类型约定写入哨兵坐标 `[0, 0]` 且不写 `location_source`，描述只说明“由你添加，保存后可在行程中搜索并定位”；
- 无法从名称判断城市的必去地点按目的城市顺序轮转放置，不猜测所属城市；
- 必去地点数量超过节奏容量时仍全部保留，并在预览提示“必去地点较多，部分日期会超过所选节奏”。

### 6.4 兴趣排序和候选选择

- 候选地点仅来自当天城市的本地点位目录；
- 命中用户兴趣的地点优先，匹配多个兴趣的优先级更高；
- 同分时按目录顺序稳定排序；
- 已作为必去地点加入的目录地点不得重复；
- 用户没有选择兴趣时使用目录默认顺序；
- 未收录城市不自动生成景点，仅保留当天的“城市安排待完善”空状态或用户必去地点。

### 6.5 节奏和时间编排

每日目标容量：

- `relaxed`：最多 2 项；
- `balanced`：最多 3 项；
- `compact`：最多 4 项。

必去地点可突破上限，普通候选地点不得突破。每天从 09:00 开始，按地点建议时长安排；相邻安排之间统一保留 30 分钟缓冲，不声称是真实交通时长。超过 19:00 后不再加入普通候选地点。

日程标题使用“城市 · 轻松漫游 / 城市探索 / 丰富体验”表达节奏。所有由目录生成的地点都标记营业时间待确认。

### 6.6 预算约束

预算仍按整团金额保存，并生成现有预算中心需要的六类 `allocations`：

- 交通 20%；
- 住宿 30%；
- 餐饮 20%；
- 门票 15%；
- 购物 5%；
- 其他 10%。

百分比应用于 `每人预算 × 人数`。前五类四舍五入到分，最后一类使用总额减去前五类，保证六类之和与总预算完全相等。

地点门票计划费用来自实际入选地点的每人估算乘人数。其余本地规划估算使用固定公式：城际交通按每位旅行者、每个目的城市 ¥120，返程时再增加每人 ¥120；住宿按 `max(旅行天数 - 1, 0) × 每人 ¥180`；餐饮按 `旅行天数 × 每人 ¥120`；市内交通按 `旅行天数 × 每人 ¥40`；其他为 0。预览必须标注“规划估算”；不为了让结果看起来不超预算而篡改地点费用。

普通候选地点受门票分类额度约束：按兴趣顺序选择时，付费地点只有在加入后不超过门票额度才可进入，免费地点仍可进入。必去地点不受此限制，即使因此超出门票额度也必须保留并产生超额提醒。这样预算会真实影响候选结果，但不会删除用户明确要求的地点。

当已知计划费用超过总预算或某分类额度时仍生成预览，并显示非阻断提醒。预算为 0 时所有分类额度为 0，已知付费地点仍显示实际计划费用。

## 7. 数据与模块边界

### 7.1 规划器接口

现有 `personalizeDemoItinerary` 替换为语义明确的纯函数：

```ts
type LocalPlanResult = {
  itinerary: Itinerary;
  notices: string[];
};

function createLocalItinerary(draft: TripDraft, options?: { id?: string; generatedAt?: string }): LocalPlanResult;
```

`options` 只用于测试与恢复时提供稳定 ID 和时间。函数不读取 `window`、`localStorage`、环境变量或网络。

### 7.2 预览缓存

创建草稿继续使用 `travel:planner-draft:v1`。新增单记录预览缓存：

```ts
type PlannerPreviewRecord = {
  version: 1;
  draft: TripDraft;
  itinerary: Itinerary;
  notices: string[];
};
```

使用键 `travel:planner-preview:v1`。读取时必须验证版本、草稿和行程核心结构；损坏记录只忽略并提示“预览无法恢复”，不得影响现有行程库。

预览缓存仅用于创建流程恢复，不属于“我的行程”。生成新预览覆盖旧预览；返回修改时删除预览缓存但保留表单草稿。

### 7.3 API 边界

本阶段创建流程统一使用本地规划器，不在有 `NEXT_PUBLIC_API_BASE_URL` 时切换到旧生成接口，避免本地与远端行为不一致。以后接 API 时，远端适配器必须返回相同的 `LocalPlanResult` 语义，并继续经过预览确认后保存。

地图服务仍只用于保存后的地点搜索与路线展示，不参与本阶段生成。

## 8. 界面与可访问性

- 预览沿用现有清新薄荷配色、按钮和卡片体系，不新增另一套视觉语言；
- 桌面端以“每日行程主栏 + 行程摘要侧栏”双栏展示，移动端单栏；
- 必去、待定位、待确认状态同时使用文字和图标，不只依赖颜色；
- 每天使用标题层级和列表语义，预算使用定义列表或可读卡片；
- 生成、保存过程使用 `aria-busy` 和可读状态文本；
- 错误使用 `role="alert"`，成功或恢复提示使用 `role="status"`；
- 主要按钮在移动端高度至少 44px；长地点名不得造成横向滚动；
- 尊重现有减少动态效果设置，本阶段不增加持续动画。

## 9. 错误与边界行为

- 无目的地、无效日期、非法天数/人数/预算：阻止生成并聚焦或明确指出首个问题；
- 天数少于城市数：允许生成，提示未排入城市；
- 必去地点超过节奏容量：允许生成，提示部分日期更紧凑；
- 未知城市：允许生成空日程和待完善提示，不编造地点；
- 同名必去地点：规范化后只保留一次；
- 本地缓存不可用：仍允许本次会话继续填写与预览，但提示刷新后可能丢失；
- 行程库保存失败：保留预览，恢复按钮状态并允许重试；
- 页面刷新：优先恢复有效预览；没有有效预览时恢复有效表单草稿；
- 已恢复预览保存成功后同时清除预览和表单草稿。

## 10. 测试与验收

### 10.1 纯函数测试

- 三种节奏产生对应的普通地点容量；
- 兴趣改变候选地点优先级；
- 已知与未知必去地点均保留、锁定且不重复；
- 多城市天数分配、天数不足提示和固定/灵活日期；
- 未知城市不产生虚构坐标或景点，只使用 `[0, 0]` 表达未定位；
- 六类额度之和精确等于整团预算；
- 预算为 0、必去地点超量、重复输入等边界；
- 同一业务输入在固定 ID/时间下产生相同结果。

### 10.2 组件与集成测试

- 填写输入生成预览但不写入行程库；
- 返回修改保留输入并使旧预览失效；
- 刷新恢复预览；损坏缓存安全忽略；
- 确认保存只创建一份行程并进入详情；
- 双击或重复提交不创建副本；
- 保存失败保留预览和重试能力；
- 预览正确展示必去、待定位、预算警告和未排入城市提示；
- 现有创建草稿、行程库、详情、预算与交通住宿测试继续通过。

### 10.3 浏览器验收

- 桌面 `1280×800` 完成填写、生成、返回修改、再次生成、保存和行程库打开；
- 移动 `390×844` 完成相同流程，无横向滚动和操作遮挡；
- 刷新恢复预览，保存后刷新不会再次出现旧预览；
- 控制台无相关错误、警告、 hydration 错误或框架错误层；
- 本阶段不部署。

## 11. 后续演进

接入外部服务时保持创建和预览流程不变，只替换数据来源：地图服务提供真实地点身份与坐标，路线服务提供实际通勤时间，AI 可在已验证候选集合上解释取舍。分享、PDF、账号与云同步作为独立阶段开发，不与本地规划器 V2 混合。
